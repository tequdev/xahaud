# Hook API cost measurement for HookFeeV2

This document is self-contained: it records why and how every Hook API's
`HOOK_API_COST` was measured, how to reproduce the measurement, the
environments used, the adopted values, and the known limitations. The raw
outputs it summarises live next to it (`RESULTS.md`, `RESULTS-linux-x86_64.md`,
`hookcost.csv`, `hookcost-linux-x86_64.csv`) and are regenerated by the
`HookAPICost` test suite described in §3.

## 1. What is being measured

HookFeeV2 prices a hook by a static worst-case *cost* computed by the guard
checker (`include/xrpl/hook/Guard.h`, `compute_wce`):

    cost = (#wasm instructions on the worst-case path) * 1
         + sum over API `call`s on that path of HOOK_API_COST(api)

and charges `cost * HookGasPrice` drops (`hook::hookCostToFee`). The unit is
"one WebAssembly instruction", so for every API in
`include/xrpl/hook/hook_api.macro`:

    HOOK_API_COST(api) = t_api / t_instr

* `t_instr` — the mean wall time of one WebAssembly instruction of typical
  compiled hook code executed by the production interpreter (WasmEdge
  0.11.2, interpreter mode, instruction counting on, exactly the
  configuration of `HookExecutor::WasmEdgeVM`). Not the cheapest opcode: the
  fee model charges every opcode 1, so the mean over the same instruction mix
  is the only self-consistent unit.
* `t_api` — the wall time one call of the API costs a validator inside the
  transaction apply: host-call boundary, host function body, and the call's
  share of synchronous side effects performed later in the same apply
  (hook-state flush, invariant checks, emitted-transaction object creation).
  The wasm `call` instruction and the argument pushes are excluded because
  they are already counted as instructions.

Both quantities are measured in the same process, on the same Release build,
with the real ledger machinery (`jtx::Env`), so absolute machine speed cancels
in the ratio. What does not cancel is the interpreter-vs-native speed ratio of
the platform, which is why the canonical numbers come from Linux x86-64 (§4).

Facts about the code base that shape the method:

* The guard checker rejects a hook whose static worst-case instruction count
  reaches 65535 (`Guard.h`, `INSTRUCTION_EXCESS`). The count is
  `loop bound x body`, so a benchmark loop calling one API can run at most
  about 5000 iterations; a 64x-unrolled body only about 40.
* Loop-head guards are consumed by the checker without being counted, so
  `HOOK_API_COST(_g, ...)` has no effect until the checker is changed. `_g`
  is still measured (§2.3).
* `HOOK_API_COST` is consumed in *static* instruction units while `t_instr`
  is measured per *runtime* instruction. Static >= runtime, so the table is
  conservative in the safe direction.
* Every API call constructs a journal in `HOOK_SETUP`
  (`include/xrpl/hook/Macro.h`), a per-call constant that, together with the
  host-call boundary, dominates the cheap APIs. It is real validator work and
  stays in `t_api`.
* Several APIs are capped per execution: `state_set`/`state_foreign_set` 256
  calls (same-key rewrites count too), `emit` 255, `etxn_nonce`/`ledger_nonce`/
  `etxn_details` 255, `hook_param_set` 16, slots 255; `etxn_reserve` and
  `hook_again` are one-shot; `accept`/`rollback` terminate.
* JTX `env(tx)` applies to the *open* ledger, where no metadata is generated
  and `finalizeHookResult` returns early. Validators run the canonical apply
  on the *closed* ledger during consensus, so everything is timed around
  `env.close()`.

## 2. Method

### 2.1 Two estimators

**E2E (end-to-end differencing)** — the table value wherever it can be
measured. Each benchmark hook loops N times (N read at runtime from a 4-byte
big-endian HookParameter, so the wasm is byte-identical across N) calling the
API K times per iteration. The same transaction is measured at N1 and N2
(10 repetitions each, minimum) on the closed-ledger apply:

    dT  = (T(N2) - T(N1)) / (N2 - N1)     ns per iteration (env.close wall time)
    dI  = (I(N2) - I(N1)) / (N2 - N1)     runtime wasm instructions per iteration
    E2E(api) = (dT - dI * t_instr - G) / K

`t_instr` (slope) and `G` (intercept: the total per-iteration cost of the
mandatory loop-head `_g` call) come from a least-squares fit of `dT` against
`dI` over pure-wasm baseline hooks (§2.2). E2E contains everything the call
causes inside the apply, needs no build flag, and is what a third party
reproduces from a Release build. A multi-API loop body (`emit` with its
`etxn_details`/`etxn_fee_base`, `slot_clear` with `slot_set`) is decomposed
by subtracting the other APIs' own E2E values; rows that cannot be decomposed
fall back to HF.

**HF (host-function timer)** — the fallback for APIs that cannot be looped
enough for differencing (capped per execution or one-shot). CMake option
`hook_cost_bench` (default OFF, never in a validator binary) defines
`HOOK_COST_BENCH`; `DEFINE_HOOK_FUNCTION` then times each host function body
into a per-API counter (`include/xrpl/hook/Bench.h`), `executeWasm` times the
wasm run, and `finalizeHookState`, `finalizeHookResult` and the invariant
visit in `ApplyContext::checkInvariantsHelper` (hook-state entries only) are
timed and attributed per modified entry / emitted transaction:

    HF(api) = (M_api - 2 * t_clk) + t_call [+ side-effect shares]

`t_clk` is the clock-read overhead and `t_call` the 0-argument host-call
boundary derived from the `hook_pos` row (body ~ 0). The boundary grows with
the number of wasm arguments (the 2-argument `_g` costs ~55 ns more than
`hook_pos` on the M3), which is why HF is the fallback, not the primary.

Table rule per row: E2E when it exists and is resolvable — propagated
per-call uncertainty `(median(T) - min(T)) / ((N2 - N1) K)` below
`max(20 ns, 10 % of E2E)` and E2E not below the physical floor
`t_call + (M - 2 t_clk)` — otherwise HF, with the reason printed. Both
estimators are printed on every row; no value is ever substituted by the
other. `state_set` / `state_foreign_set` are HF by construction: their E2E
is far larger (about 21 us per *created* and 5 us per *modified* hook-state
entry on the Linux host) and that excess is genuine closed-apply work
(SHAMap leaf and path rehash, node-store write, metadata, owner-directory
insert), but it is a cost per ledger *entry* rather than per API call, it
depends on the node-store backend, and ledger growth is what the owner
reserve prices. `RESULTS*.md` list it separately under "Apply-time ledger
cost (not charged by HOOK_API_COST)".

### 2.2 Baselines: `t_instr` and `G`

Body: byte-wise buffer walk compiled from C at -O2 (local.get/set, i32
load/store, add/xor/and, compare, br_if) unrolled 1/2/4/8/16/64 times, each
with its own N1/N2 fitting its static budget. The loop bodies contain no Hook
API call; the only host call per iteration is the mandatory `_g`, which is
constant across the six hooks and therefore lands in the intercept `G`, not
in the slope. Gates: `R^2 > 0.998`, `SE(G)/G < 15 %`, and the runtime `dI`
must match the guard checker's own per-iteration count within 40 % (catches
compiler unrolling). Two extra bodies (pure i64 arithmetic; memory-copy
heavy) give a sensitivity range for `t_instr` and agreed with the fit within
20 % on both platforms.

### 2.3 `_g`

`_g`'s per-call cost is the intercept `G` (the per-iteration time not
explained by `dI * t_instr`, taken with no API in the loop body) divided by
`t_instr`. The harness prints it in the family table and the proposed block.
It is applied to the table like any other API, with the caveat that the guard
checker does not charge loop-head guards today.

### 2.4 Success-path discipline

Every benchmark hook checks every call: any host-API error return rolls back
with that code, and each API's documented success value is asserted on every
call (`emit == 32`, `util_verify == 1`, `state == written length`,
`sto_validate == 1`, `util_keylet == 34`, ...). A rollback makes the
repetition `tecHOOK_REJECTED`, which the harness skips and reports with the
return code; a row with no successful repetition is listed under "Not
measured", never folded into a cost. The test additionally asserts that
`emit` rows created one emitted-transaction object per call and `state_set`
rows wrote one entry per call. This discipline found two hooks that had been
measuring a failure path (`sto_validate` on an over-long buffer; `prepare`
exhausting the 255 emit nonces after call 255).

### 2.5 Scenarios and sizes

| API | scenario |
|---|---|
| `accept`, `rollback` | HF, one call per execution, mean over 200 (the clock ticks every 41.67 ns on Apple Silicon; a minimum would always select the low tick) |
| `etxn_reserve`, `hook_again` | HF, first call; later calls are `ALREADY_SET` |
| `emit` | `etxn_reserve(200)`, 200 emits each with its own `etxn_details`; decomposed; the window includes emitted-txn object creation and the TxQ injection at close |
| `state`, `state_foreign` | reads are cached per key: 200 *distinct* pre-created keys per execution, disjoint key ranges per size; foreign reads pass the 32-byte namespace explicitly |
| `state_set` | `_create` (fresh keys every repetition via a salt parameter) and `_modify` (fixed keys); table = max |
| `state_foreign_set` | HookGrant on the foreign account; K = 1 (first call, grant scan) and K = 200; table = first call |
| `slot_set` | 34-byte keylet form only (the 32-byte txid form hits the master transaction cache) |
| `slot_*`, `otxn_slot`, `meta_slot`, `xpop_slot` | explicit slot numbers (slot 0 allocates and exhausts 255) |
| `hook_skip` | two hooks installed; flags alternate 1/0 |
| `hook_param_set` | K = 16 (cap) |
| `meta_slot` | the hook calls `hook_again()` in the strong pass and loops `meta_slot` in the weak pass; both inside the same close |
| `xpop_slot` | on a `ttIMPORT` transaction with the `ImportTCAccountSet` fixtures, one Env per fixture |
| `util_verify` | passing ed25519 and secp256k1 verifications; table = max |
| `util_keylet` | every type the implementation accepts (AMM and DID in their own Env with the amendment enabled); table = max. BRIDGE, XCHAIN_*, MPTOKEN*, CREDENTIAL, PERMISSIONED_DOMAIN return INVALID_ARGUMENT unconditionally on this branch and TICKET has no case, so they cannot be measured |
| `float_sto` | XRP / IOU / short-form; table = max |
| `trace*` | early-return at production journal level; measured as such |
| `ledger_keylet` | lower bound on a near-empty JTX ledger |

Size families and the value used for the table: `util_sha512h` 32 B / 1 KiB /
16 KiB -> 1 KiB; `sto_*` ~30 B / ~250 B (real tx) / ~4 KiB -> 250 B;
`state*` 32 B / 256 B / 4096 B (ExtendedHookState) -> 256 B; `otxn_field`,
`otxn_slot`, `slot` 20 B / 1 KiB / 16 KiB -> 1 KiB; `otxn_param`,
`hook_param`, `hook_param_set` 32 B / 256 B -> 256 B (hard cap); `prepare`,
`emit`, `etxn_fee_base` minimal Payment / Invoke + 1 KiB Blob -> 1 KiB. Rule:
the reference-size value, unless `cost(largest) / cost(reference) > 10`, in
which case the geometric mean of the two (this fires for `util_sha512h`).
The reports print the fitted `a + b*size` line and the largest-size value.

### 2.6 Aggregating runs (common baseline)

The API times reproduce to well under 1 % between runs and batches, but the
baseline fit's `t_instr` drifts by about 10 % between batches on a VM. A
ratio taken per run therefore inherits the baseline's noise. The adopted
table is computed from the pooled data instead: per API, the median over all
quality runs of (per-run table value x that run's `t_instr`) — the API's wall
time in ns at the §2.5 table rule — divided by the median `t_instr` over the
same runs. `_g` is the pooled median of `G` over the pooled `t_instr`.

### 2.7 Rounding

Values with three or more digits are rounded up to two significant digits,
two-digit values are rounded up to one significant digit
(1234 -> 1300, 123 -> 130, 39 -> 40, 12 -> 20).

### 3.1 Files


### 3.2 Build and run

The suite refuses to run outside a Release (`NDEBUG`) build: a Debug build's
unoptimised host functions inflate every ratio while the Conan-built WasmEdge
stays optimised.

```sh
cmake -S . -B build-release -DCMAKE_BUILD_TYPE=Release -Dtests=ON -Dhook_cost_bench=ON   # with the conan toolchain file
cmake --build build-release --target rippled
./build-release/rippled --unittest=HookAPICost --unittest-jobs=1 --unittest-arg=docs/hook-api-cost
```

`HookAPICost` is a manual suite (never part of a full `--unittest` pass).
`--unittest-jobs=1` is required; run on an otherwise idle machine. A run
takes about 15 s and writes `RESULTS.md` and `hookcost.csv` into the
`--unittest-arg` directory. Repeat the run several times, keep the runs whose
baseline fit passes the gates (`SE(G)/G < 15 %`, `R^2 > 0.998`), and
aggregate as in §2.6; a single run is a draft. Expect a run-to-run spread of
1.2x on a desktop and up to 1.3x on a VM after rounding.

### 3.4 Regenerating the benchmark wasm

After editing `hookcost.c` run `src/test/app/hookcost/build.sh` (needs
`wasmcc` from wasienv, `hook-cleaner`, `shasum`/`sha256sum`, optionally
`clang-format`). Every loopable hook uses the shared
`BENCH_BEGIN(MAXITER)` / `BENCH_END` scaffold; `MAXITER` must keep the hook's
static worst-case count under 65535. The reliable way to size it is to ask
the guard checker directly (`validateGuards(wasm, std::nullopt, "", false,
hook_api::getImportWhitelist(rules), hook_api::getGuardRulesVersion(rules))`
returns the count instantly) and target 55,000-60,000. The runtime guard
counter is cumulative across the whole execution, so a nested `GUARDM` must
declare `outer_bound * inner_bound`; the baselines avoid nesting entirely.
`maxiterTable()` in the test must be kept in sync with `hookcost.c`.

The interpreter is about 1.6x slower per instruction on the Linux VM while
the host functions are not, which is why most Linux ratios come out lower
than the M3 draft. `util_sha512h` and `util_verify` on the M3 use ARM SHA-512
hardware acceleration that x86-64 validators do not have; the Linux values
are the ones adopted. The per-API comparison with the 1.5x gate of the
original design is kept in `RESULTS-linux-x86_64.md`'s companion data for
reference; it is informational only.

## 6. Limitations and follow-ups

* The Linux host is a VM: the baseline drifts about 10 % between batches
  (absorbed by §2.6) and individual runs need the fit gates. A bare-metal
  x86-64 run with the same procedure would tighten the spread; the API times
  themselves already reproduce to under 1 %.
* The interpreter-vs-native ratio differs between validator machines by up to
  about 1.5x (M3 vs x86 VM here). A single-platform table with round-up is
  the practical compromise.
* `HOOK_API_COST(_g)` is measured but has no effect until the guard checker
  counts loop-head guards.
* The apply-time ledger cost of creating or modifying hook-state entries is
  reported but not charged; a per-created-entry charge is a separate policy
  decision for HookFeeV2.
* Cheap APIs sit at 50-70 because the host-call boundary (about 270 ns on the
  Linux host, 47 units) and `HOOK_SETUP`'s journal construction dominate
  them; APIs that read the ledger (`state` 410, `slot_set` 320) are clearly
  separated from those that read the in-memory transaction (`otxn_param` 80).
* Applying the table changes the values that `EXPECT_HOOK_COST` asserts in
  `SetHook_test.cpp` and related suites; those expectations must be updated
  together with `hook_api.macro`.
